# The governed delivery loop

A coding task crosses several authorities. Treating them as one prompt hides the
moment at which intent becomes implementation and implementation becomes evidence.

Enclosure keeps the sequence explicit:

1. **Intent** — people accept the relevant requirements and diagrams.
2. **Context** — the registered workspace and task select applicable guidance.
3. **Change** — the agent works inside those constraints on an issue branch.
4. **Verification** — tests and project health evaluate observable behavior and
   architecture against exact inputs.
5. **Evidence** — findings and attestations identify what was checked.
6. **Acceptance** — a human decides whether the implementation is ready to move.
7. **Delivery** — repository and board state record what actually shipped.

Each boundary matters because a later green signal cannot retroactively create an
earlier decision. Passing tests do not accept a design. A valid architecture
attestation does not merge a pull request. An agent completing a tool call does
not authorize the next phase.

The loop is useful precisely because it refuses to turn confidence into authority.
